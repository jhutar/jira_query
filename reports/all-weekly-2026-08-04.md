# Team Konflux
* **Weekly Overview:** Significant strides were made in securing cluster environments through ServiceAccount migrations, resolving critical Enterprise Contract violations, and scaling out test infrastructure. The team also finalized Quay.io scaling baselines and successfully bootstrapped 140 virtualized SNO spoke clusters in ScaleLab to establish a robust ArgoCD GitOps baseline.
* **What was done:**
  - Resolved `verify-conforma` image access and EC trust violations in probe runs by pinning and updating task references in the templates repo ([KONFLUX-15147](https://redhat.atlassian.net/browse/KONFLUX-15147)).
  - Pinned Tekton git-resolver references to specific, immutable commit SHAs to eliminate GitLab/GitHub rate-limiting (HTTP 429) errors under high concurrent build volumes, and configured a nightly Jenkins automation pipeline to dynamically update these SHAs ([KONFLUX-14479](https://redhat.atlassian.net/browse/KONFLUX-14479)).
  - Finalized and shared a one-page Quay.io monitoring and load baseline with the Quay-QE team, establishing a concrete path to assess whether the registry can support a projected 100x Konflux build growth ([KONFLUX-15081](https://redhat.atlassian.net/browse/KONFLUX-15081)).
* **What is moving:**
  - In-depth investigations into cluster performance revealed `kube-controller-manager` lease timeouts caused by extreme etcd object/event churn from Tekton tasks. Post-defragmentation event counts dropped 87% (1.25M to 161K) but operators continue to crash-loop on `stone-prd-rh01` and `stone-prod-p02` under load; support cases remain actively open with SRE ([KONFLUX-15216](https://redhat.atlassian.net/browse/KONFLUX-15216)).
  - Initial manual replication of the ArgoCD Agent Mode setup was completed by successfully deploying an MNO Hub and bootstrapping 140 virtualized SNO VM spokes registered under ACM; a standalone follow-up task has been created to validate documentation and ensure independent reproduction ([KONFLUX-15131](https://redhat.atlassian.net/browse/KONFLUX-15131), [KONFLUX-15270](https://redhat.atlassian.net/browse/KONFLUX-15270)).
  - Caching proxy (Squid) performance experiments are in progress. Initial results show that caching enabled can paradoxically increase wall clock build times due to resource noise, prompting efforts to gain read-only namespace access to analyze Squid container logs directly ([KONFLUX-15199](https://redhat.atlassian.net/browse/KONFLUX-15199)).

# Team Pipelines
* **Weekly Overview:** The team successfully delivered a fully automated Python-based report generation pipeline that queries Horreum directly, while rolling out integrated Tekton Results performance metrics and nine revamped Grafana dashboards. Major progress was also made in identifying concurrency regressions and mapping out Tekton resolver performance profiles across versions 1.22 and 1.23.
* **What was done:**
  - Integrated OpenShift Pipelines CPT change-detection alerts in Horreum to directly deliver notification payloads to the `#forum-pipelines-cpt-alerts` Slack channel, utilizing a newly merged `ChangeToSlackWebhook` HttpAction formatter ([SRVKP-13078](https://redhat.atlassian.net/browse/SRVKP-13078)).
  - Integrated Tekton Results performance tests with Horreum and Prow while deploying 9 unified Grafana dashboards (5 new dashboards plus 4 refactored to use shared libraries), enabling side-by-side version comparisons (nightly vs. baselines) for pipeline, chains, and results metrics ([SRVKP-12483](https://redhat.atlassian.net/browse/SRVKP-12483)).
  - Concluded a feasibility study for Grafana MCP and instead built a robust Python-based report generation CLI (`generate_comparison.py`) that queries the Horreum PostgreSQL database directly, using MAD-based outlier detection to output structured JSON and LLM-assisted markdown KB articles ([SRVKP-12533](https://redhat.atlassian.net/browse/SRVKP-12533), [SRVKP-11997](https://redhat.atlassian.net/browse/SRVKP-11997)).
* **What is moving:**
  - Investigations into PipelineRun success rate degradation at concurrency 16+ in Pipelines 1.23 revealed that aggressive QBT (Quota Burst Tuning) combined with HA deployments starts 320 concurrent reconcilers (compared to the default of 20). This 16x thread expansion saturates the API server and results in a 17.6% failure rate at concurrency 20 compared to stable HA-only runs ([SRVKP-13124](https://redhat.atlassian.net/browse/SRVKP-13124)).
  - Resolver performance regression testing is actively underway for versions 1.22 and 1.23; the team reduced cluster provisioning requirements by merging parameter sweeps and pushed a bug fix to resolve duration calculation errors in multi-namespace environments ([SRVKP-13158](https://redhat.atlassian.net/browse/SRVKP-13158)).

# Team Satellite
* **Weekly Overview:** Reached a major milestone by publishing the official Satellite Capsule Server High Scalability blog live on redhat.com. Technical investigations also progressed deeply into persistent connection reuse for RHSM smart-proxies and resolving API concurrency race conditions that block client registrations.
* **What was done:**
  - Formally revised and published the Red Hat Satellite Capsule Server High Scalability blog live on redhat.com, highlighting verified capacity gains and scaling baselines ([SAT-34272](https://redhat.atlassian.net/browse/SAT-34272), [SAT-30540](https://redhat.atlassian.net/browse/SAT-30540)).
* **What is moving:**
  - Investigations into persistent upstream connection reuse for forwarded RHSM smart-proxy traffic reached review phase; the outbound client transport path was migrated to Faraday using `faraday-net_http_persistent` to reduce TCP/TLS handshake latency, with a PR submitted ([SAT-45802](https://redhat.atlassian.net/browse/SAT-45802)).
  - Investigations continue into high-concurrency Foreman API provisioning race conditions that insert orphaned hosts with `NULL` types, blocking client registrations. Upstream Rails 7.0 upgrades are currently in code review as part of the resolution path ([SAT-46037](https://redhat.atlassian.net/browse/SAT-46037)).
  - An OpenShift Virtualization POC utilizing `jetlag` is being scoped to validate Satellite/Capsule provisioning integration over location-specific subnets, modeling Capsule network attachments to isolated subnet segments ([SAT-45791](https://redhat.atlassian.net/browse/SAT-45791)).
